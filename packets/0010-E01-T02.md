## Context

T01 moved the guard and the denylist into the `cost-guard` repository and gave them a
composite-action interface. It is released: `martcoca/cost-guard@v1` (moving major tag) and
`@v1.0.0` (immutable). The action takes a **plan file path**, not stdin.

This packet makes the first consumer actually consume it, and deletes its local copies.
Until a consumer stops carrying its own copy, nothing has been de-duplicated — there is
just a fourth copy.

`platform-azure` is first because it is the hardest of the three. Getting it right here
makes `platform-aws` and `platform-gcp` mechanical.

### Three traps, all found before you started

They were reported in T01's evidence file. None is hypothetical.

**1. `scripts/check-ci-contract.sh` asserts the exact command string.** Lines 123–124
require these literals inside `guarded-plan.yml`:

```
'tofu plan -input=false -no-color -json 2>"$RUNNER_TEMP/tofu-plan.err" | bash scripts/cost-guard.sh /dev/stdin'
'>"$RUNNER_TEMP/cost-guard.out" 2>"$RUNNER_TEMP/cost-guard.err"'
```

Replacing the pipeline with the action makes both assertions fail. **`check-ci-contract.sh`
must change in this same commit.** It is easy to miss because the failure surfaces in a
script you are not otherwise editing.

**2. The current invocation pipes and recovers exit codes via `PIPESTATUS`.** The action
takes a file path deliberately: reading an exit code from a pipeline has already produced a
wrong conclusion in this organization. Redirect the plan to a file, then pass the path.

**3. `guarded-plan.yml` runs on `push` to `main` only.** `pull_request` is explicitly
forbidden by the contract check. Do not "improve" this by adding a pull-request trigger.

### The one real design decision

`scripts/check-denylist-agreement.sh` compares `config/cost-guard-denylist.json` against
`config/azure-policy-denylist.json`, proving the Azure Policy denylist and the guard
denylist agree in both directions. **It is Azure-specific and stays in this repository** —
T01 correctly declined to port it, because moving it would have meant copying an Azure
Policy artifact into a cloud-neutral repository.

But deleting the local `config/cost-guard-denylist.json` breaks it, and that check is
load-bearing: it is the only thing asserting that what Azure Policy denies server-side and
what the guard denies at plan time are the same set. **Losing it silently is the worst
outcome of this packet.**

Choose how it gets the guard denylist and justify it. Two shapes worth weighing:

- **Read it from the action checkout**, so the comparison uses exactly the version CI runs.
- **Keep a vendored mirror**, with a check that fails when it drifts from the pinned
  upstream release. This reintroduces a copy, so it needs the drift check to be worth it.

A third option — dropping the agreement check — is not available. If neither shape works,
stop and say so.

## Goal

`platform-azure` runs the released cost guard, holds no copy of it, and its Azure Policy
agreement check still proves the two denylists match.

## Boundary

**This repository only.** Do not modify `cost-guard`, `platform-aws`, or `platform-gcp`.

Do not change what is denied. No type added, none removed, no price string edited. If the
released denylist differs from the local one, **stop** — that is a finding, not a merge
conflict to resolve.

Do not apply anything to Azure, do not touch Azure Policy assignments, and do not alter
OIDC or IAM configuration. Plan-time only.

Pin the action to a tag, never to `main`.

## Done when

- `guarded-plan.yml` invokes `martcoca/cost-guard@v1` (or `@v1.0.0`) instead of a local
  script, passing a plan **file path**, with the exit code read from the step rather than
  from a pipeline.
- `scripts/cost-guard.sh` and `config/cost-guard-denylist.json` are **deleted** from this
  repository.
- `scripts/check-ci-contract.sh` is updated in the same commit and passes, asserting the
  new invocation with the same strictness it asserted the old one — including that the
  guard still runs before any apply.
- `scripts/check-denylist-agreement.sh` still passes, still fails when the two lists
  disagree, and its negative case still demonstrates that.
- The three exit outcomes still gate the pipeline: a denied create fails the job, a clean
  plan passes, and an undecidable plan **fails** rather than passing.
- No workflow gains a `pull_request` trigger.

## Check

From the repository root, with no cloud authentication:

```bash
scripts/check-ci-contract.sh          # exits 0 against the rewritten workflow
scripts/check-denylist-agreement.sh   # exits 0, and still fails on a seeded disagreement
scripts/test-cost-guard.sh 2>/dev/null || echo "removed with the local guard — expected"
! test -f scripts/cost-guard.sh
! test -f config/cost-guard-denylist.json
```

Then the part that is the actual contract, and cannot be argued from the diff:

1. **Show the action refusing a denied plan in CI**, and the job failing. A fixture plan
   containing a denied create is enough; it needs no cloud.
2. **Show an undecidable plan failing the job**, not passing. This is the fail-closed
   property and it is the one most easily lost when moving to a wrapper.
3. **Seed a disagreement** between the Azure Policy denylist and the guard denylist, show
   `check-denylist-agreement.sh` fails, and restore it.
4. **Show `check-ci-contract.sh` failing** if the guard step is removed from the workflow.
   A contract check that passes an unguarded pipeline is worse than none.

## Notes

The exit code must come from the action step, not from a pipeline. `cmd | head` reports
`head`'s status, and that has already produced a wrong conclusion here.

If the action turns out to be awkward for this workflow — the plan file, the token, the
working directory — that is a finding about the interface T01 chose, and it is worth more
than a clean result. Report it rather than working around it silently.

Report what you could not verify. An honest gap is a result; a silent one is a defect.
