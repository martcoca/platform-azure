# T05: platform-azure reports a stale pin

- **Initiative:** 0010 — Cost Guard
- **Epic:** E02 — a consumer cannot be silently behind
- **Packet id:** `0010-E02-T05`
- **Executor:** `worker`
- **Target:** The `platform-azure` repository
- **Approval:** none
- **Shape:** `execution`
- **Status:** done
- **Source:** initiatives/0010-cost-guard/E02-staleness/T05-azure-adopts-freshness.md

## Context

T01 built the freshness action. T02 fixed a guard that took 391 seconds on a real plan and
released `v1.0.2`. **Neither of those tells this repository when it is running an old guard.**

That is not hypothetical any more. Between `v1.0.1` and `v1.0.2` this repository was pinned
to a guard that stalls for six and a half minutes on a realistically-sized plan, and nothing
here said so. It was fixed because a human happened to notice a slow job — which is exactly
the detection mechanism this epic exists to replace.

T05 established that propagation is manual: three pull requests, every time. Detection does
not change that. **It changes whether anyone knows a bump is owed.**

## Goal

This repository reports, in its own CI, when the cost guard pin it uses is behind the
current release — and cannot fail to notice indefinitely.

## Boundary

**This repository only.** Do not modify `cost-guard` or the other two consumers.

**Do not change the guard's verdict path.** Freshness is a separate signal. A network
failure looking up the current release must never turn a denied plan into a clean one, and
must never fail a build whose plan is fine.

Do not change the pin as part of this packet unless it is already stale — and if it is, say
so and bump it in a separate commit so the two changes are separable.

Do not change what is denied.

## Done when

- **The freshness action runs beside the existing guard step**, with `if: always()`. A
  denied plan fails the guard step, and that is exactly when knowing the pin is stale
  matters most.
- **A scheduled run exists** that reports staleness whether or not anyone pushes. T01's
  evidence is explicit that a repository nobody pushes to is the one most likely to drift,
  and incidental pushes are not a detection strategy.
- **`fail-on-stale` is `false` on pull requests and `true` on the scheduled run.** Staleness
  must not block work unrelated to the guard, and must not be ignorable either. If you
  choose differently, say why.
- **Unknown freshness reports as unknown**, never as current. Demonstrate the lookup failing.
- **The verdict is unaffected either way.** Show a denied plan still failing and a clean plan
  still passing while the freshness lookup is broken.
- The contract check covers the new step, so removing it fails CI rather than passing quietly.

## Check

From the repository root:

```bash
scripts/check-ci-contract.sh
```

Then demonstrate, with output in the pull request:

1. **A CI run showing the freshness verdict** on the current pin. Link it.
2. **Pin deliberately to `v1.0.1`** on a scratch branch and show the action reporting the
   repository as behind, naming both versions. Restore.
3. **Break the lookup** — an unreachable endpoint or a bad token — and show it reports
   *unknown*, not *current*, and that the build's guard verdict is unchanged.
4. **Show the contract check failing** when the freshness step is deleted from the workflow.
5. State when the scheduled run fires and what it does when the pin is stale.

## Notes

The value of this is entirely in the case nobody is watching. A signal that only appears
when someone is already looking at the job adds nothing to what a human eye already does.
Weigh the schedule accordingly.

If the action turns out to be awkward here — the pin lives in `config/cost-guard-action.txt`
and in every `uses:`, and this repository's contract check asserts they match — that is a
finding about T01's interface and worth reporting rather than working around.

Write `evidence/0010-E02-T05.md`, including what a stale pin actually looks like in this repository's
CI, so the next person recognises it.
