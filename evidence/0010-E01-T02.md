# 0010-E01-T02 — platform-azure consumes the released cost guard

`platform-azure` now runs `martcoca/cost-guard@v1.0.0` as a composite action and carries
no copy of the guard or its denylist. `scripts/cost-guard.sh`,
`config/cost-guard-denylist.json` and `scripts/test-cost-guard.sh` are deleted.

## Before anything else: the released denylist is the local one

The Boundary said to stop if the released denylist differed from the local one. It does
not. The file at both `v1` and `v1.0.0` is byte-identical to the deleted local copy:

```
5991b73f9a7f1719c5f2885e996183bee9131e63f1a0bdcb04a5f7c86d6c8c43  config/cost-guard-denylist.json (deleted local copy)
5991b73f9a7f1719c5f2885e996183bee9131e63f1a0bdcb04a5f7c86d6c8c43  v1 / v1.0.0 (git show, and the GitHub raw contents API at ref=v1.0.0)
```

`scripts/cost-guard.sh` was likewise byte-identical (`31bddb59…`). Nothing about what is
denied changed in this packet.

## The design decision: where the agreement check gets the guard denylist

**Chosen: read it from the pinned release. No vendored mirror.**

`scripts/check-denylist-agreement.sh` no longer reads a local file. It resolves the guard
denylist in exactly two ways, and refuses to run if neither works:

- `COST_GUARD_DENYLIST=<path>` — CI sets this to an `actions/checkout` of the release at
  the pinned ref, so the comparison uses the same bytes the plan job's action carries.
- unset — the script fetches `config/cost-guard-denylist.json` from the release named in
  `config/cost-guard-action.txt` via `gh api` at that ref. This is what a local run does.

Why not the mirror: a mirror plus a drift check is two files and a third failure mode to
keep honest, and its only advantage — working offline — buys nothing here, because CI is
the only place the verdict matters and CI has the release checked out anyway. The mirror
would also have been the fourth copy this initiative exists to remove.

Three properties make the "no local file" version safe rather than merely smaller:

1. **It cannot pass by not happening.** No denylist supplied and no way to fetch one is
   exit 2, never exit 0. So is a denylist that is not a non-empty JSON array — an empty
   array would otherwise satisfy one of the two directions silently.
2. **The pin has one source.** `config/cost-guard-action.txt` holds
   `martcoca/cost-guard@v1.0.0`. `check-ci-contract.sh` asserts every
   `uses: */cost-guard@…` in every workflow equals it, and that the agreement job checks
   out that same ref. The workflow pin and the compared-against version cannot drift.
3. **The pin is immutable.** `@v1.0.0`, not the moving `@v1`. Both were permitted. `@v1`
   would let what is denied change here with no commit in this repository, which is the
   thing the Boundary's "do not change what is denied" is protecting; a denylist update
   should be a deliberate bump of one line in `config/cost-guard-action.txt`.

## 1 & 2. The action refuses a denied plan, and an undecidable plan fails too

Run locally against a checkout of the release at `v1.0.0`, driving the action's real
entrypoint under the environment contract the runner provides (`GITHUB_ACTION_PATH`,
`INPUT_PLAN`, `GITHUB_OUTPUT`) — the same six inputs the deleted `test-cost-guard.sh`
covered, now going through the action instead of a local script:

```
plan-clean.json                  exit=0  verdict=allow       exit-code=0
plan-with-nat.json               exit=1  verdict=deny        exit-code=1
plan-events-with-nat.jsonl       exit=1  verdict=deny        exit-code=1
plan-errored.jsonl               exit=2  verdict=undecidable exit-code=2
plan-unrecognizable.txt          exit=2  verdict=undecidable exit-code=2
(empty file)                     exit=2  verdict=undecidable exit-code=2
```

Undecidable is not softer than denied: both are non-zero and both fail the step.

The same six are asserted in CI by the `action-contract` job in
`.github/workflows/cost-guard.yml`, which resolves `uses: martcoca/cost-guard@v1.0.0` on
a real runner — the half a local shell run cannot cover, since binding `uses:`, the
inputs and the step outputs is the runner's job.

**What I did not do, deliberately:** the CI demonstration asserts
`steps.<id>.outcome == 'failure'` on steps carrying `continue-on-error`, rather than
letting a job go red. A job that genuinely fails cannot live in this repository — the
merge gate requires every check green, so a permanently-red demonstration job would block
every pull request forever. `outcome == failure` is the same fact recorded instead of
acted on, and it is the pattern T01 used in the action's own `manifest` job. The real
gate is `guarded-plan.yml`, where the guard step has no such excuse and
`check-ci-contract.sh` forbids one anywhere in that file.

## 3. Seeded disagreement, both directions, then restored

The guard denylist is upstream and must not be touched, so the disagreement is seeded in
`config/azure-policy-denylist.json`, which is this repository's own artifact. Both
directions of the comparison were exercised:

```
$ jq 'map(select(.azure_type != "Microsoft.Network/azureFirewalls"))' … > config/azure-policy-denylist.json
$ scripts/check-denylist-agreement.sh
Denied by the cost guard but not by Azure Policy:
  azurerm_firewall (Azure Firewall, ~$900+/mo)

The denylists disagree. ADR-0039 requires one list expressed two ways.
exit=1

$ jq '. + [{"azure_type":"Microsoft.Test/neverGuarded","tofu_types":["azurerm_never_guarded"]}]' … 
$ scripts/check-denylist-agreement.sh
Denied by Azure Policy but absent from the cost guard:
  azurerm_never_guarded (covered by Policy as Microsoft.Test/neverGuarded)

The denylists disagree. ADR-0039 requires one list expressed two ways.
exit=1

$ # restored
$ git diff --quiet config/azure-policy-denylist.json && echo restored
restored
$ scripts/check-denylist-agreement.sh
Denylists agree (…).
exit=0
```

And the case that matters most now that the denylist is remote — the check refusing to
report agreement it did not perform:

```
$ COST_GUARD_DENYLIST=/…/there-is-no-denylist-here.json scripts/check-denylist-agreement.sh
Missing guard denylist: /…/there-is-no-denylist-here.json
Refusing to report agreement against a denylist that is not there.
exit=2
```

All four are steps in the `denylist-agreement` job, so they run on every push, not only
here.

## 4. `check-ci-contract.sh` fails on an unguarded pipeline

Four ways to lose the gate, each seeded into `guarded-plan.yml` and then restored:

```
remove the guard step        → Missing required contract text …: uses: martcoca/cost-guard@v1.0.0        exit=1
excuse it with continue-on-error → Forbidden contract text …: continue-on-error                          exit=1
pipe the plan into the guard again → Missing required contract text …: >"$RUNNER_TEMP/tofu-plan.json" …  exit=1
unpin to @main               → Workflow uses martcoca/cost-guard@main but the pin … is @v1.0.0           exit=1
restored                     → CI contract checks passed.                                                exit=0
```

The contract check also now asserts what the old string-match could not: that the guard
step follows the plan step by line number, that no `tofu apply|destroy|import|taint|state
rm|mv|push` appears in the guarded-plan workflow, and that neither `scripts/cost-guard.sh`
nor `config/cost-guard-denylist.json` is present or tracked — a re-vendored copy fails CI.
The pre-existing "workflows must not apply infrastructure" assertion is unchanged.

`guarded-plan.yml` still triggers on `push` to `main` and `workflow_dispatch` only. No
workflow gained a `pull_request` trigger; `require_absent 'pull_request'` on that file is
untouched.

## What I could not verify

- **The CI runs themselves, at the time of writing.** Everything above is local. The
  runner-level facts — that `uses: martcoca/cost-guard@v1.0.0` resolves from this
  repository, that the composite action's outputs bind on a failed step, that
  `actions/checkout` of a second public repository into `.cost-guard-release` works — are
  asserted by the new jobs but were proven by T01's equivalents, not by me. Whoever reads
  this after the pull request has the actual run.
- **`guarded-plan.yml` end to end.** It needs Azure OIDC and only runs on `push` to
  `main`, so no pull request exercises it. What was verified is the guard half in
  isolation; the `tofu plan` → file → action wiring is asserted by the contract check and
  reviewed, not executed. This gap existed before this packet too.
- **`--live`** was not run. It needs an authenticated `az`, and reading a live Azure
  Policy assignment is outside a plan-time packet.
- **Exit-2 output shape.** The action's step-summary text for a denial or an undecidable
  verdict was not compared against the old workflow's summary text. Both fail the job;
  only the prose differs.

## Notes for whoever does platform-aws and platform-gcp

- **A finding about T01's interface, small but real:** the composite action fails the step
  on exit 1 and exit 2 with no way to distinguish them from the *step* alone. `outcome` is
  `failure` for both, and telling deny from undecidable needs `steps.<id>.outputs.verdict`.
  That is fine — the outputs exist and they work — but a consumer that only checks
  `outcome` cannot report which verdict it got, and the natural way to reach for outputs
  on a failed step is a `continue-on-error` that also removes the gate. The two clouds
  that follow should copy the shape in `guarded-plan.yml` here: no excuse on the guard
  step, and a separate `if: always()` reporting step that reads the output and re-fails.
- The three traps the packet named are all real and all bit in the expected order. Trap 1
  is the one that would have been missed: `check-ci-contract.sh` fails in a script you
  have no other reason to open.
- The Azure agreement check is Azure-specific and has no counterpart in the other two
  repositories, so `platform-aws` and `platform-gcp` should be materially smaller — the
  workflow swap, the two deletions, and their own contract checks.
- `config/cost-guard-action.txt` plus a contract assertion that every `uses:` matches it
  is worth copying. It is what makes "the version CI runs" and "the version compared
  against" the same string by construction rather than by discipline.
