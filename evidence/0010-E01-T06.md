# 0010-E01-T06 — anchor the Azure contract check

Every structural assertion in `scripts/check-ci-contract.sh` now matches a whole line.
A comment cannot satisfy one. 54 assertions moved from fixed-string `grep -F` to an
anchored `require_line`; zero unanchored `require` calls remain.

## The defect, demonstrated both ways against the same file

`tests/fixtures/ci-contract/guarded-plan-guard-commented-out.yml` is a copy of
`guarded-plan.yml` with the guard step deleted and replaced by a comment naming it.

**The pre-change check, taken from `main`, run against that file:**

```
$ bash scripts/check-ci-contract.sh
CI contract checks passed.
exit=0
```

A workflow with no guard step at all. The check said it was fine.

**The anchored check, same file:**

```
Missing required contract line /uses: martcoca/cost-guard@v1\.0\.1/ in .github/workflows/guarded-plan.yml.
It must be a real YAML line, not a mention of one in a comment.
exit=1
```

## Check

```
$ scripts/check-ci-contract.sh
CI contract checks passed.
exit=0

$ scripts/test-ci-contract.sh
PASS  the real workflows pass the contract check
PASS  a guard step replaced by a comment fails the check (exit 1)
PASS  and says the line must be real rather than a mention in a comment
PASS  a commented-out uses: @main is not scanned as a real pin
PASS  a real uses: @main is rejected as unpinned

Contract check tests passed.
exit=0
```

Scenarios 3 and 4 are the `uses:` scanner. Anchored, it no longer lifts
`martcoca/cost-guard@main` out of the middle of a comment and reports the workflow as
unpinned on the strength of a line that runs nothing — while a real `uses: …@main` line is
still rejected against the pin. The old `grep -o` form did the opposite of both.

Also green: `check-workflow-permissions.sh` (5 workflows), `check-automerge-coverage.sh`
(4 awaited), `post-merge-workflows.sh check`, `check-evidence.sh`, `bash -n` over every
script, and a YAML parse of all five workflows.

## What is anchored and what is not, and why

**Anchored (`require_line`, 54 assertions).** Everything whose target is a whole line:
the `output "x" {` blocks and their `sensitive = true`; `backend.tf`, `versions.tf`, the
bootstrap override, the `.gitignore` negation, the two README commands; every `publish`
mapping and both body lines of `publish-github-secrets.sh`; every trigger, permission,
toolchain pin, `TF_VAR_*` env line and step id in `guarded-plan.yml` and
`azure-identity.yml`; the `uses:` pin, the plan path, `GUARD_OUTCOME`, `GUARD_VERDICT`,
the `|| exit 1` re-assertion; and in `cost-guard.yml` the pin, the release `ref:`, the
`assert` lines and the three agreement-case `- name:` lines.

The four verdict strings were a `for` loop doing a fixed-string search for
`echo "allow" >> "$GITHUB_STEP_SUMMARY"`. They are now five explicit anchored lines,
including the three `case` branches, each matched as the real line it is.

**Deliberately not anchored — six `require_absent` patterns and four inline greps.** These
assert that text is *absent*, or that text appears *anywhere*:

- `require_absent` on `pull_request`, `continue-on-error`, `cost-guard.sh|/dev/stdin|PIPESTATUS`,
  `client-secret|ARM_CLIENT_SECRET`, and the two on the helper and identity workflow.
  Over-matching a forbidden pattern is the safe direction: a *commented-out* `pull_request`
  trigger still fails, which is what you want. Anchoring these would weaken them.
- `grep -Fq 'REDACTED-'` on the tfvars example, `grep -Fq 'github_repository'`, the
  `default` scan inside the `resource_group_name` variable block, and the `git grep` for
  committed GitHub URLs. All are "does this text occur at all" questions, not line
  questions.

The `require` helper itself is kept, unused, for shape parity with
`../platform-gcp/scripts/check-ci-contract.sh`, with a comment saying what it is for.
Deleting it would diverge the three consumers; that divergence is how the duplication this
initiative removed grows back.

## A finding, and the one thing I changed outside the stated boundary

**`scripts/check-ci-contract.sh` was never run by CI in this repository.** Nothing under
`.github/` invoked it. It appeared only in two comments inside `guarded-plan.yml` and in
the README's list of local checks. The packet's premise is that this check "is what stands
between a plan and an apply" — here it stood nowhere, and had not since it was written.
That is a larger hole than the comment defect: a gate a comment satisfies at least runs.

This forced a decision. The Boundary says `check-ci-contract.sh` **and its tests** only,
and "do not change any workflow". The Done-when requires the negative fixture to be
"committed and exercised by CI, not run once by hand". Nothing in CI executes a script it
is not told to, so those two cannot both hold literally.

I added **one step**, to `guard.yml`, and nothing else:

```yaml
      - name: The CI contract check holds its own contract
        run: scripts/test-ci-contract.sh
```

I read "do not change any workflow" as protecting the workflows *under test* — the clause
lists it beside the pin, the denylist, and what is denied — and `guard.yml` is the harness
that runs contract checks, not a thing this check asserts about. The step is the minimum
that satisfies "exercised by CI", and it closes the finding above as a side effect, since
the tests' first scenario runs the real check against the real tree.

The check now also asserts that step exists, anchored:

```bash
require_line 'run: scripts/test-ci-contract\.sh' "$contract_workflow"
```

so the tests cannot be quietly unhooked. `guarded-plan.yml`, `cost-guard.yml`,
`azure-identity.yml`, `config/cost-guard-action.txt` and the denylists are untouched —
`git diff` over `.github/workflows/` is the three added lines above and nothing else.

I also added one assertion that did not exist before: `GUARD_VERDICT`. The reporting step
reads it, the reference check asserts it, and it was the only load-bearing line in that
step going unasserted. Naming it here rather than leaving it in a diff.

## How the tests work, and why they are not a second copy of the check

`scripts/test-ci-contract.sh` builds a throwaway git tree from this repository's tracked
files — a real one, because the check uses `git grep` and `git ls-files` — swaps in one
file, and runs the **real** `scripts/check-ci-contract.sh` against it. No assertion is
re-implemented. A test that re-states what the check does proves only that two copies
agree with each other.

## What I could not verify

- **No CI run existed when this was written.** Everything above is local. Whoever reads
  this after the pull request has the actual run of the new `guard.yml` step.
- **Tightening revealed no non-conformant workflow.** The Boundary said to stop and report
  if it had. The check passed against the real workflows on the first run after every
  conversion, and each anchored regex was verified against the real file rather than
  reasoned about — but "passes" is evidence the regexes match, not proof that each one
  still means what its fixed-string ancestor meant. I read each conversion against the
  target line; I did not mutate every asserted line individually to prove each assertion
  can still fail. Scenarios 2–4 prove that for the guard step and the pin, which are the
  load-bearing ones.
- **The fixture is a snapshot.** If `guarded-plan.yml` changes, the fixture will not track
  it automatically. It is not regenerated from the real file at test time, because a
  fixture derived from the file under test would silently follow that file's own defects.

## Notes for platform-aws and platform-gcp

- **`platform-gcp` has the same untested gap this repository had**, in the other
  direction: it asserts `require_line 'run: scripts/check-ci-contract\.sh'` on its contract
  workflow, so the check runs there — but it has no committed negative fixture and no test
  script. It demonstrated the defect by hand. `scripts/test-ci-contract.sh` and
  `tests/fixtures/ci-contract/` here are the missing half and should port cleanly; the
  scratch-tree helper needs no Azure-specific knowledge.
- **A residual all three share:** the anchoring only reaches assertions whose target is a
  whole line. In this repository every one of them turned out to be a whole line, including
  the shell lines inside `run:` block scalars — but that was luck of formatting, not
  design. A future assertion about a fragment in the middle of a longer line would have to
  reach for the unanchored `require`, and the defect would be back for that one assertion.
  Worth a shared convention rather than three independent judgements.
