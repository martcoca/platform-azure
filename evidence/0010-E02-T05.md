## What a stale pin looks like here

This is the thing to recognise. Run through the released action's own entrypoint at `@v1`,
with the pin set to `v1.0.1` and `fail-on-stale` as the schedule sets it:

```
cost-guard freshness: behind — pinned to v1.0.1 (93fada3); the current release is v1.0.2 (b2721b4)
::warning title=cost-guard is out of date::pinned to v1.0.1 (93fada3); the current release is v1.0.2 (b2721b4)
cost-guard freshness: failing the step because fail-on-stale is set.
[step exit=1]

status=behind
pinned-ref=v1.0.1
pinned-commit=93fada3e1d3760860e72d1ee5887494bb975f73a
latest-release=v1.0.2
latest-commit=b2721b4cf80e097ba5ca20a8b897f4dc05b8869c
```

and in the job summary:

> ### Cost guard pin: behind
> pinned to v1.0.1 (93fada3); the current release is v1.0.2 (b2721b4)
> A denial added after `v1.0.1` is **not in force here**. Bump the pin.

In CI that is a red `Cost guard freshness` scheduled run, a warning annotation, and that
summary. To clear it: edit `config/cost-guard-action.txt` and every `uses:` that carries the
version, in one commit. `scripts/check-ci-contract.sh` fails if they disagree.

## Decisions this packet left open

**Schedule: daily, 06:23 UTC.** The packet asked me to weigh it. A release can land on any
day, and a weekly cadence means up to seven days running a guard whose newest denial is not
in force — this epic exists because exactly that went unnoticed once. The cost is one API
call. GitHub emails the repository owner when a scheduled workflow fails on the default
branch, which is the notification; note that GitHub also disables scheduled workflows after
60 days of repository inactivity, so a truly abandoned repository still goes quiet.

**`fail-on-stale` is `${{ github.event_name == 'schedule' }}`** — true on the schedule,
false on pull requests and manual dispatch, exactly as the packet asked.

**The freshness action is pinned to `@v1`, not to the guard's `@v1.0.2`.** This is the one
deliberate asymmetry and it needs stating. The guard is pinned immutably so that what is
denied cannot change without a commit here; the reporter denies nothing, so that reason does
not apply to it. The deciding fact is that **`freshness/action.yml` does not exist at
`v1.0.1`** — the very release this repository was stuck on when the slow guard went
unnoticed. A consumer pinned there could not have run the reporter at all: `uses:
martcoca/cost-guard/freshness@v1.0.1` does not resolve, and the step would error rather than
report `behind`. A detector pinned to the artefact whose staleness it detects breaks at
exactly the staleness it exists to detect. `scripts/check-ci-contract.sh` derives the ref
from `config/cost-guard-action.txt` (`${slug}/freshness@${major}`), so it still cannot drift
to another repository or to a branch. The cost is that the reporter's code can change under
us within `v1`; the worst case is a wrong report, never a wrong verdict.

## Two findings about T01's interface

**1. A failed lookup writes unparseable lines into `$GITHUB_OUTPUT`, and that can fail the
step.** `resolve()` and the `latest_tag` lookup run `gh api … --jq …`, and on a non-2xx `gh`
prints the JSON error body to **stdout**. It is captured as if it were a value. With a bad
token the outputs file becomes:

```
status=unknown
pinned-ref=v1.0.2
pinned-commit={
  "message": "Bad credentials",
  "documentation_url": "https://docs.github.com/rest",
  "status": "401"
}
latest-release={
  ...
}
```

Eight of those lines are not `key=value` and are not wrapped in the `<<DELIMITER` form
Actions requires for multi-line values. The runner rejects such a file with `Invalid format`
and fails the step. In the plan job that would fail a guarded plan whose plan is fine —
precisely what this packet's Boundary forbids.

I could not fix it: the Boundary is this repository only. **So the freshness step carries
`continue-on-error`** — `true` in the plan job, and
`${{ github.event_name != 'schedule' }}` in the scheduled workflow, so it reports without
blocking everywhere except the schedule, where being able to go red is the point. That is a
mitigation, not a fix. The fix belongs in `cost-guard`: capture `gh api` output only on
success, or strip anything that is not a 40-character hex SHA.

This forced narrowing a rule 0010-E01-T06 had just added. `continue-on-error` was forbidden
anywhere in `guarded-plan.yml`; it is now forbidden *everywhere except the freshness step*,
checked by counting occurrences and confirming the single one sits inside that step. Test
scenario 8 asserts that excusing the **guard** step still fails, so the protection that
mattered is intact.

**2. The `pin` input's description invites a mistake that reports confidently and wrongly.**
It reads "Point it at the same string the guard's `uses:` carries, or at the pin file that
string is checked against." The script does not read files — it string-splits on `@`. Passing
the path, as that sentence invites:

```
$ INPUT_PIN='config/cost-guard-action.txt' … bash scripts/freshness.sh
cost-guard freshness: behind — pinned to config/cost-guard-action.txt ({"messa); the current release is v1.0.2 (b2721b4)
cost-guard freshness: failing the step because fail-on-stale is set.
exit=1
```

A **false `behind`**, naming `{"messa` as a commit — the first seven characters of a 422 body
— and under `fail-on-stale` it fails the build. Same root cause as finding 1. It matters
beyond the typo: any non-2xx on the commits endpoint, including a transient 5xx, can produce
a false `behind` rather than `unknown`, and on the scheduled run that is a false red. I
avoided it by passing the file's *contents*, read in a step, in both workflows.

## What I could not verify

- **No CI run existed when this was written.** The `Cost guard freshness` workflow runs on
  `pull_request`, so this pull request produces demonstration 1 — the freshness verdict on
  the current pin — and whoever reads this after has it.
- **Demonstration 2 was not run in CI.** Showing `behind` on a scratch branch needs the
  workflow to exist on the default branch first, since `workflow_dispatch` resolves from
  there. The alternative — a branch whose pin is deliberately `v1.0.1` with a pull request
  open — risks auto-merge landing a deliberately stale pin, which is not a risk worth taking
  for a demonstration. It is shown above through the released action's real entrypoint
  instead. After this merges, the CI version is:

  ```
  gh workflow run "Cost guard freshness" --ref <scratch-branch-pinned-to-v1.0.1>
  ```

- **The `Invalid format` step failure is reasoned, not observed here.** I confirmed the
  malformed `$GITHUB_OUTPUT` empirically; that Actions rejects those lines and fails the step
  is documented runner behaviour I did not reproduce on a runner. The mitigation holds either
  way, and if the runner turns out to tolerate it, `continue-on-error` on a pure reporter is
  still correct.
- **The scheduled run has never fired.** First occurrence is 06:23 UTC the day after merge.
- **Nothing was applied to Azure.** No Policy, OIDC or IAM change; no `tofu apply`.
